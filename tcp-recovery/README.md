# TCP 패킷 복구 시간 측정 도구

`response_tcp.sh` / `request_tcp.sh`로 하던 기존 측정 방식(수동 `iptables`, Wireshark로 눈으로 확인)을
대체하는 도구 모음. 목표는 "클라이언트가 패킷 유실을 인식한 시점부터 서버가 재전송한 패킷을 받기까지의
시간"을 자동으로, 재현 가능하게 측정하는 것.

## 두 가지 방법

**1. 기본 - 양쪽에서 스크립트 하나씩 (SD 측정과 같은 방식).** 서버(예: Thor)에서 `response_tcp.sh`,
클라이언트(예: Orin)에서 `request_tcp.sh`를 각자 실행한다. 둘 사이에 SSH가 필요 없다.
`request_tcp.sh` 쪽 화면/로그에 뜨는 `패킷 유실 복구 시간: Xus` 줄이 바로 그 값이다 - `request-sd.cpp`가
"매칭까지 처리 시간"을 찍는 것과 같은 방식으로, **클라이언트 자신이 직접 잰다.**

**2. 교차검증 - 서버 쪽 tcpdump 캡처 하나로 계산 (시계 동기화 불필요).** 아래 도구들:

- [inject_loss.sh](inject_loss.sh) - 선로 패킷 유실을 흉내내는 도구 (start/stop). 1번 방법에서도
  `response_tcp.sh`가 내부적으로 이걸 쓴다.
- [analyze_recovery.py](analyze_recovery.py) - 서버 쪽 tcpdump 캡처 하나로 복구 시간을 계산 (원리는
  아래 "왜 서버 캡처만으로 되나" 참고)
- [tune_tcp_recovery.sh](tune_tcp_recovery.sh) - 복구 시간을 줄이는 커널 설정 적용 (양쪽 방법 공통).
  재부팅 후 한 번만 실행하면 됨 - 매 테스트 실행 전에 다시 돌릴 필요 없음. `../tune-latency.sh`와
  같이 한 번에 적용하려면 `../tune-all.sh <피어 IP>` 참고.
- [run_experiment.sh](run_experiment.sh) - `inject_loss.sh`+캡처+`analyze_recovery.py`를 SSH로 묶어
  한 번에 실행하는 편의 스크립트 (이 프로젝트의 Thor↔Orin 구성 전용)

**둘의 차이:** 1번은 클라이언트 애플리케이션이 직접 재는 값이라 vsomeip 자신의 수신측 처리, 그리고
vsomeip 내부의 정체불명의 송신 지연(아래 "발행 주기가 왜 중요한가" 참고 - `--cycle`을 짧게 잡으면
피해간다)까지 포함된 "체감" 값이다. 2번은 tcpdump로 잡은 TCP 세그먼트만 보는 순수 와이어 레벨 값이라
더 정밀하지만, 서버 쪽에 tcpdump를 따로 띄워야 한다. **둘 다 필요할 때만 쓰면 된다 - 1번이 기본,
이상하다 싶으면 2번으로 대조.**

## 왜 새로 만들었나

기존 `README.md`의 방법(`sudo iptables ... -D INPUT ... -j DROP`)에는 세 가지 문제가 있었다.

1. **`-D`는 규칙을 삭제하는 옵션이다.** 적힌 그대로 실행하면 애초에 유실이 주입되지 않는다.
2. **`OUTPUT`에서 `DROP`하면 선로 유실이 되지 않는다.** 보낸 쪽 TCP 스택이 전송 실패로 인식해 그
   세그먼트를 "보낸 적 없음"으로 되돌리고 다음 쓰기에서 다시 큐에 넣는다. 실제 선로 유실(세그먼트가
   상대에게 도달하지 못했지만 보낸 쪽은 성공으로 아는 상황)과는 다른 상황이라 재전송 타이머가 정상적으로
   동작하지 않는다.
3. **Wireshark 수동 측정**은 캡처 위치가 netfilter보다 앞이라 실제로 유실된 패킷도 화면에 보이고, 두
   장비의 시계가 다르면 "클라이언트 인식 시점"을 정의할 방법이 없다.

## 왜 서버 캡처만으로 되나 (2번 방법의 핵심 아이디어)

"클라이언트가 유실을 인식한 시점 → 복구 패킷을 받은 시점"은 클라이언트 쪽에서 재야 할 것 같지만, 실제로는
**서버 쪽 캡처 하나로 계산할 수 있다.**

- 클라이언트가 유실을 알아채는 계기가 되는 패킷("트리거", 구멍 바로 다음에 온 세그먼트)과 그 뒤에 오는
  재전송 패킷은 **둘 다 서버 → 클라이언트로 같은 경로를 지난다.**
- 두 패킷의 편도 지연은 (경로가 같으므로) 사실상 같아서 서로 상쇄된다.
- 그래서 `t_클라이언트(재전송 도착) - t_클라이언트(트리거 도착) ≈ t_서버(재전송 송신) - t_서버(트리거 송신)`
  가 성립하고, 우변은 **서버에서 잰 두 송신 시각의 차이**이므로 클라이언트 시계를 볼 필요가 없다.

`analyze_recovery.py`가 계산하는 `[C]`가 바로 이 값이다.

## 사용법

### 1. 기본 - 양쪽에서 스크립트 하나씩

```bash
# 서버 (예: Thor) - sudo 필요 (유실 주입/tcpdump에 iptables/ip route를 쓴다)
sudo ./response_tcp.sh <클라이언트 IP> [주기ms=1] [1/N 유실=8] [최소유실건수=10]

# 클라이언트 (예: Orin) - sudo 불필요
./request_tcp.sh [주기ms=1] [임계배수=3.0] [최소유실건수=10]
```

양쪽 다 최소유실건수(기본 10)만큼 감지하면 스스로 멈추고 요약을 찍는다 - Ctrl-C나 `timeout`으로 죽일
필요 없음. **서버 쪽은 이제 클라이언트를 SSH로 조종하거나 나중에 `run_experiment.sh`를 따로 돌릴 필요
없이, 실행 중에 바로 와이어 레벨 값(`[wire] ...`)을 자기 화면에 찍는다** (`analyze_recovery.py --live`
가 서버 쪽 `tcpdump`를 실시간으로 분석) - client 로그의 "패킷 유실 복구 시간"과 나란히 놓고 바로
비교할 수 있다:

```
# 클라이언트 화면
첫 이벤트 수신, seq=1748
[loss] seq 1749 -> 1750: 복구 시간 2745us (수신 간격 3745us, 기준 1062us)
...
총 수신 345건 중 10건 유실, 평균 복구 시간 2783us

# 서버 화면 (동시에)
[wire] 유실 복구 확인: 561us  (누적 1건)
...
[wire] 총 발행 320건 중 10건 유실, 평균 복구 시간(wire) 559us
```

두 값의 n(건수)이 서로 다를 수 있다 - 두 도구가 각자 독립적으로 자기 `--min-losses`에 도달하면 그
즉시 멈추고 연결을 끊기 때문으로, 측정 오류가 아니다. 자세한 내용은 아래 "결과: 실측값" 참고. 서버
쪽은 상대가 먼저 끊어 트래픽이 끊기면 5초 뒤 자동으로 같이 종료된다.

**주기 기본값이 1ms인 이유, 임계배수가 3.0배인 이유는 아래 "발행 주기가 왜 중요한가" 참고.**
"기준" 값(위 예시의 1062us)은 `--cycle`을 그대로 믿는 게 아니라 **최근 정상 수신 간격의 중앙값에서
자동으로 계산된다** - 그래서 `--cycle`이 서버와 안 맞아도(예: 서버는 1ms인데 클라이언트에 실수로 5를
줬다든가) 예전처럼 유실을 통째로 못 잡는 사고는 안 난다. 처음 5건까지만 `--cycle` 값을 잠정 기준으로
쓰고, 그 뒤로는 실측값으로 넘어간다.

**그래도 주기를 바꿨다면 `--threshold`는 다시 확인할 것.** `NO_DROP=1 sudo ./response_tcp.sh
<클라이언트 IP>`로 유실 주입 없이 돌려서 `[loss]`가 안 뜨는지 본다(오탐 확인). 기본값
(`--cycle 1 --threshold 3.0`)은 이 프로젝트의 유선 직결 링크에서 오탐 0건으로 확인됐다.

### 2. 교차검증 - 직접 조합해서 쓰기 (다른 두 장비, 다른 트래픽 패턴)

```bash
# 1) 서버 실행 (평가하려는 실제 SOME/IP 서버, 또는 notify-sample 같은 예제)

# 2) 유실 주입 시작
sudo ./tcp-recovery/inject_loss.sh start <서버 IP> <클라이언트 IP> PORT=<TCP 포트>

# 3) 캡처하면서 클라이언트 실행
sudo tcpdump -i <인터페이스> -n -tt --time-stamp-precision=micro -w cap.pcap "tcp port <포트>" &
# ... 클라이언트 실행 ...
sudo kill %1

# 4) 유실 주입 해제
sudo ./tcp-recovery/inject_loss.sh stop <서버 IP> <클라이언트 IP>

# 5) 분석
tcpdump -r cap.pcap -n -S -tt --time-stamp-precision=micro > cap.txt
python3 ./tcp-recovery/analyze_recovery.py --capture cap.txt --port <포트>
```

**주의:** `analyze_recovery.py`는 `-S`(절대 시퀀스 번호)와 `-tt`(epoch, 마이크로초) 옵션으로 만든 텍스트
캡처가 필요하다. 상대 시퀀스 번호로는 구멍(hole) 탐지 로직이 의미가 없어진다.

이 프로젝트의 Thor↔Orin 2대 구성이라면 1)~4)를 SSH로 자동화한 [run_experiment.sh](run_experiment.sh)를
대신 써도 된다:

```bash
sudo -E ./tcp-recovery/run_experiment.sh <라벨> stream 1 40 \
    --server-ip <서버 IP> --client-ip <클라이언트 IP> --client-host <user>@<클라이언트 IP> --client-sudo
```

**주기는 꼭 `1`로 줄 것** - 아래 "결과: 실측값"에 있는 좋은 숫자는 전부 `--cycle 1`에서 나온 것이고,
예전에 쓰던 `--cycle 5`는 이유는 다르지만(발행 주기 문제가 아니라 RACK 재정렬 타이밍) 결과가 몇 배
나쁘다. `--client-sudo`는 원격의 vsomeip 체크아웃이 root 소유일 때만 필요; SSH 로그인은 키 기반 권장,
안 되어 있으면 `export SSHPASS=...` 후 `sudo -E`로 실행 - **비밀번호를 파일이나 명령행에 직접 적지
말 것**, 자세한 내용은 스크립트 상단 주석 참고. 결과는 `tcp-recovery/results/<라벨>/`에 남는다
(`.gitignore`에 등록되어 있음 - 커밋하지 말 것).

### 트래픽 패턴이 중요하다

**유실 뒤에 다른 세그먼트가 이어서 오지 않으면 클라이언트는 유실을 알 방법이 없다.** 한 번에 하나씩
요청-응답을 주고받는 락스텝(lockstep) 트래픽(예: `request-sample`/`response-sample`)이 정확히 이 경우다
- 응답이 유실되면 클라이언트는 다음에 보낼 것이 없어 SACK을 만들 수 없고, 복구는 전적으로 서버의
재전송 타이머(RTO)에만 의존한다. 실측 218ms.

`request-tcp-recovery`/`response-tcp-recovery`(방법 1)는 처음부터 유실 뒤로도 계속 이어지는 주기적
이벤트 스트림이라 이 문제가 없다 - 서버가 매 주기 시퀀스 번호를 담은 이벤트를 계속 발행하고, 클라이언트는
그 도착 간격을 본다 (락스텝 옵션 자체가 없음). `run_experiment.sh`(방법 2)의 `stream` 모드도 동일한
이유로 같은 패턴(`notify-sample`/`subscribe-sample`)을 쓴다. `rr` 모드(요청-응답 락스텝)는 이 문제를
직접 보여주는 경로 점검용으로만 남겨뒀다.

## 결과: 실측값

### 유선 직결 링크 (2026-09, 현재)

Thor↔Orin을 스위치 대신 이더넷 케이블로 직결한 뒤(자세한 내용은 CHANGES_THOR.md "Direct Ethernet Link"
참고) 다시 잰 값. 최초 전송의 1/8 유실.

**`--cycle 5`(구 기본값)에서 `--cycle 1`로 바꾼 게 지금까지 중 가장 큰 한 방이었다** - 이전까지의
모든 와이어 레벨 측정은 `--cycle 5`로 했었는데, `--cycle 1`로 처음 재보니 완전히 다른 숫자가 나왔다:

| | 주기 | n | mean | p50 | p90 | ≤2ms |
|---|---|---|---|---|---|---|
| 방법 2 (와이어 레벨), `--cycle 5`(구), 튜닝 없음 | 5ms | 45 | 2.70ms | 0.57ms | 5.63ms | 58% |
| 방법 2 (와이어 레벨), `--cycle 5`(구), + 튜닝 | 5ms | 47 | 2.39ms | 0.57ms | 5.63ms | 64% |
| **방법 2 (와이어 레벨), `--cycle 1`, 튜닝 없음** | **1ms** | 92 | **0.59ms** | 0.57ms | 0.59ms | **100%** |
| **방법 2 (와이어 레벨), `--cycle 1`, + 튜닝** | **1ms** | 71 | **0.58ms** | 0.56ms | 0.57ms | **100%** |
| 방법 1 (애플리케이션 레벨), 구 기본값 | 5ms, 임계 2.0 | 12 | 7.43ms | - | - | - |
| **방법 1 (애플리케이션 레벨), 현재 기본값** | **1ms, 임계 3.0** | 10건씩 수 회 반복 | **2.73~2.78ms** | - | - | - |

`--cycle 1`에서는 **와이어 레벨이 이미 목표(2ms)를 여유 있게 통과한다** - 평균 0.58~0.59ms, 개별
건 100%가 2ms 이내. `net.ipv4.tcp_recovery`(RACK)를 꺼서 비교도 해봤는데(mean 1.19ms) 켜진 기본값이
더 빨랐다 - RACK을 의심했던 이전 가설은 틀렸다.

**남은 문제는 방법 1(애플리케이션 레벨)이 방법 2(와이어 레벨)를 못 따라간다는 것이다** (2.7ms대 vs
0.58ms) - `--cycle`을 서버와 안 맞게 줘서 생기는 기준선 문제가 아니다(자동 보정 기준선으로 확인:
실측 "기준 주기"가 ~1.06ms로 `--cycle 1`과 거의 일치했다). **직접 계측 완료(2026-09-15)** - vsomeip
자신의 `receive_cbk`(io 스레드) → `on_message`(main-dispatch 스레드) → 사용자 콜백 경로는 평균
~24µs(최대 75µs)로, 원인이 아님을 확인. 지연은 `receive_cbk`가 호출되기 **이전**, 즉 NIC 도착부터
커널이 그 사실을 vsomeip에 알리기까지의 구간에 있다 - NIC 인터럽트 coalescing(512us 고정, 드라이버가
`ethtool -C` 값 변경을 전부 거부), CPU idle state/거버너(이미 `jetson_clocks`로 최적화되어 있어 더
줄일 여지 없음), GRO, IRQ affinity, 프로세스 real-time 스케줄링(`chrt`)까지 다 시도했지만 전부 무효 -
자세한 표와 커널 틱(`CONFIG_HZ=250`) 근거는 `CHANGES_THOR.md` "Live wire-level display, cross-board
hardening, and a real self-calibration bug" 참고. **결론: 유선 직결 이후로는 커널 재빌드 없이 이 구간을
더 줄일 방법을 찾지 못했다.**

남은 꼬리(`--cycle 5`의 p90 5.6ms)는 튜닝해도 거의 안 줄었다 - 아래 "2ms까지 남은 구간"에서 설명하는 커널 틱
(`CONFIG_HZ=250`) 문제가 여전히 원인으로 보인다. 링크를 바꾼 것만으로는 이 부분이 해결되지 않는다.

**양방향 테스트(2026-09-15, `--min-losses 60`, 버그 수정 후):** client/server 역할을 바꿔가며(Thor↔Orin
둘 다 client 역할로) 재확인한 결과, 와이어 레벨은 방향과 무관하게 552-560us로 아주 일관적인데
(100% ≤2ms, 흔들림 없음), **애플리케이션 레벨은 Thor가 client일 때가 Orin이 client일 때보다 뚜렷하게
느리고 변동폭도 크다** (p90 11.1ms, max 11.5ms vs Orin client의 p90 2.9ms, max 2.9ms) - 둘 다 동일하게
`jetson_clocks`/성능 거버너가 적용되어 있는데도 이렇다. 원인은 아직 안 팠음 (Thor의 NIC 드라이버가
Orin의 `nvethernet`과 다른 점, 코어 수/토폴로지 차이 등이 후보) - `CHANGES_THOR.md` "Next steps" 참고.

| | n | mean | p50 | p90 | max |
|---|---|---|---|---|---|
| 애플리케이션 레벨, server=Thor/client=Orin | 60 | 2753us | 2707 | 2871 | 2911 |
| 애플리케이션 레벨, server=Orin/client=Thor | 60 | 4865us | 3851 | 11086 | **11550** |
| 와이어 레벨, server=Thor/client=Orin | 38 | 559us | 557 | 564 | 592 |

client/wire의 표본 수(n)가 다른 이유는 측정 오류가 아니다 - 두 도구가 각자 독립적으로 `--min-losses`에
도달하면 그 즉시 스스로 멈추고 연결을 끊는데, 어느 쪽이 먼저 도달하느냐에 따라 남은 쪽의 카운트가
그 시점까지 확인한 것으로 끊긴다 (방향은 실행마다 바뀔 수 있음 - 위 두 행이 정반대 방향으로 갈린 게
그 증거). 자세한 경위(재현·원인·수정한 진짜 버그 포함)는 `CHANGES_THOR.md` 같은 절 참고.

### Wi-Fi 시절 (참고, 이전 실측)

#### 방법 1 (클라이언트 자체 로그, 애플리케이션 레벨)

Thor(서버, 유선) → Orin(클라이언트, Wi-Fi), `--cycle 5`, 최초 전송의 1/8을 유실시킨 실측 (튜닝 없음):

| | n | mean | p50 | min | max |
|---|---|---|---|---|---|
| 유실 주입 (`복구 시간`) | 21 | 9.7ms | 9.6ms | 6.8ms | 17.3ms |
| 유실 없음 기준선 (`NO_DROP=1`, 자연 지터) | 2 / 594건 (0.3%) | - | - | 7.2ms | 8.5ms |

방법 2의 [C](아래, 튜닝 후 3.46ms)보다 눈에 띄게 높다. 이유는 두 가지가 겹쳐서다.

1. **이 값은 vsomeip 자신의 수신측 처리 시간을 포함한다** (방법 2는 순수 와이어 레벨).
2. **더 크게는, vsomeip이 요청한 주기대로 실제로 데이터를 배달하지 못한다.** 유실을 전혀 주입하지
   않아도 20초에 594건(초당 ~30건)만 도착했다 - 요청한 주기(초당 200건)의 15% 수준.
   > **정정 (직접 계측으로 확인).** 처음엔 서버 로그의 `wait_until_sent: Maximum wait time for send
   > operation exceeded`를 근거로 서버 쪽 TCP 송신 흐름 제어(`tcp_server_endpoint_impl`의
   > `wait_until_sent`)가 발행 루프 자체를 막고 있다고 봤는데, `app_->notify()` 호출과 발행 루프
   > 전체 반복 시간을 직접 재보니 **둘 다 요청한 주기(1ms) 그대로, 매 반복 정상이었다** - 클라이언트
   > 연결 여부와 무관하게. 즉 서버는 실제로 매 1ms마다 정상적으로 `notify()`를 계속 호출하고 있다.
   > 그 로그 줄은 진짜였지만 10초짜리 타임아웃(`VSOMEIP_MAX_TCP_SENT_WAIT_TIME`)이 어쩌다 한 번
   > 걸린 것뿐, 20초 내내 이어지는 병목의 원인은 아니었다. 그렇다면 병목은 `notify()` 호출 이후,
   > vsomeip 내부 송신 큐 또는 `boost::asio::async_write` 완료 체인 어딘가에 있다는 뜻인데,
   > 정확히 어디인지는 더 파보지 않았다 (vsomeip 내부 코드를 읽어야 하는 영역 - CHANGES_THOR.md의
   > "Follow-up 2" 참고).

이 자체가 흥미로운 결과다: 부담이 큰 주기에서는 **패킷 유실이 없어도** vsomeip의 TCP 발행이 목표
주기를 못 따라간다.

##### 발행 주기가 왜 중요한가

`--cycle`을 1/5/20/50ms로 바꿔가며 실측한 결과(2026-09, 유선 직결 링크, `NO_DROP=1`, 20초):

| `--cycle` | 이론치 | 실측 | 효율 | 실제 간격 (=이론치/실측) |
|---|---|---|---|---|
| 1ms | 20000건 | 2831건 | 14.2% | ~7.1ms (요청의 7.1배) |
| 5ms | 4000건 | 594건 | 14.8% | ~34ms (요청의 6.7배) |
| 20ms | 1000건 | 151건 | 15.1% | ~132ms (요청의 6.6배) |
| 50ms | 400건 | 61건 | 15.2% | ~328ms (요청의 6.6배) |

**중요: 효율이 요청한 주기와 무관하게 ~15%로 일정하다.** 즉 **주기를 길게 잡아도 처리량이 정상화되지
않는다** - 이전 버전의 이 문서는 "주기를 넉넉하게 잡을 것"을 권했는데, 이는 실측으로 틀린 것으로
확인됐다. 오히려 반대다: 실제 발행 간격이 항상 요청 주기의 ~6.7배이므로, **요청 주기를 짧게 잡을수록
실제 발행 간격도 비례해서 짧아진다** - 유실이 나면 다음 정상 이벤트("트리거")가 그만큼 빨리 도착해서
복구 감지가 촘촘해지고, 방법 2(와이어 레벨)의 값에 더 가까워진다. 그래서 `request_tcp.sh`/
`response_tcp.sh`의 기본값을 `--cycle 1 --threshold 3.0`으로 바꿨다 - 실측 평균이 7.4~7.8ms(구
기본값 `--cycle 5 --threshold 2.0`)에서 **2.7ms**로 내려가 방법 2의 값(2.4~2.7ms)과 거의 일치한다
(오탐 0/2828건, 재현 2회 확인: mean 2727us/2760us). vsomeip의 TCP 송신 경로 자체를 고치지 않는 한
이 ~15% 효율(~6.7배 지연)은 없어지지 않는 것으로 보이며, 원인은 파보지 않았다 - host/network 설정이
아니라 vsomeip 코드를 봐야 하는 영역이다.

#### 방법 2 (서버 캡처, 와이어 레벨)

```
재전송: SACK 계기 48건, 타이머 계기(RTO/TLP) 0건
  [B] SACK 수신 -> 재전송 송신 (서버 반응 시간)        : n=48 mean=1971us p50=10us ...
  [C] ★ 클라이언트 기준 복구 시간 (요청하신 지표)      : n=48 mean=3414us p50=1510us p90=6354us max=10822us  (<=2ms: 56%)
```

- **[C]가 요청하신 지표다.** "클라이언트가 유실을 인식 → 복구 패킷 수신"에 해당.
- **[B]**는 참고용: 서버가 SACK을 받고 재전송을 내보내기까지 걸린 시간 (서버 자체의 반응 지연, 원인
  분석용).
- **타이머 계기(n건)**: 이 캡처만으로는 시간을 잴 수 없는 재전송(직전 SACK이 캡처에 없음 - RTO/TLP로
  복구됐다는 뜻). `[C]`에는 포함되지 않는다. 이 값이 크면 트래픽 패턴이 락스텝에 가깝다는 신호.

## `tune_tcp_recovery.sh`가 하는 일과 실측 효과

TCP **서버**(재전송을 보내는 쪽) 에서 실행. 두 설정 모두 휘발성(재부팅하면 사라짐)이고 되돌리는 명령을
출력해 준다. **재부팅마다 한 번만 실행하면 된다** - 그 뒤로 `response_tcp.sh`/`request_tcp.sh`를
몇 번을 돌리든 다시 적용할 필요 없다. `../tune-latency.sh`와 순서를 신경 쓸 필요도 없다 - 서로 다른
설정을 건드리므로(하나는 CPU/NIC, 하나는 TCP 커널 파라미터) 어느 쪽을 먼저 실행해도 상관없다.
`sudo ../tune-all.sh <피어 IP>`로 둘을 한 번에 적용할 수 있다.

| 설정 | 무엇을 하나 | 왜 |
|---|---|---|
| `ip route ... rto_min 1ms` | 해당 피어로 가는 경로에만 최소 재전송 타임아웃을 낮춤 | 커널 기본값(200ms)은 SACK으로 못 잡는 경우(락스텝 트래픽, 버스트의 마지막 세그먼트)의 하한선. SACK 경로 자체는 이 타이머까지 가지 않으므로 빠르지 않음 |
| `sysctl tcp_reordering=1` | **호스트 전체**의 SACK 재정렬 임계값을 낮춤 | 커널 기본(3)은 순서 뒤바뀜과 진짜 유실을 구분하려고 기다리는 시간. 순서가 안 바뀌는(직결에 가까운) 링크에서는 이 대기가 그대로 지연으로 남음. 순서가 실제로 바뀌는 링크(다중경로, 로밍 등)에서는 쓰지 말 것 |

Thor(서버, 유선) → Orin(클라이언트, Wi-Fi), 5ms 주기 SOME/IP 이벤트, 최초 전송의 1/8을 유실시킨 실측
(`[C]`, 클라이언트 기준 복구 시간):

| 설정 | mean | p50 | n |
|---|---|---|---|
| 기본값 | 6.51ms | 1.90ms | 292 |
| + `rto_min 1ms` | 4.07ms | 2.11ms | 273 |
| + `rto_min 1ms` + `tcp_reordering=1` | **3.46ms** | **1.64ms** | 293 |

## 2ms까지 남은 구간 (Wi-Fi 시절 분석 - `--cycle 5` 기준)

**유선 직결 + `--cycle 1`에서는 와이어 레벨(방법 2)이 이미 2ms를 넉넉히 통과한다** (평균 0.58ms,
100% ≤2ms) - 아래 분석은 `--cycle 5`였던 시절 기록이라 지금은 해당 없음. 지금 2ms를 못 넘는 건
애플리케이션 레벨(방법 1, ~2.7ms)뿐이고, 원인은 위 "유선 직결 링크" 절 참고.

최선 조건(3.46ms, `--cycle 5` 기준)을 분해하면:

| 구성 요소 | 평균 기여 |
|---|---|
| Wi-Fi 왕복 지연 | 1.47ms |
| 서버가 즉시 반응한 경우 (61%, [B] ≤100us) | ≈0 |
| **서버가 3~10ms 대기 (RACK 재정렬 타이머, 커널 틱 단위)** | **1.61ms** |
| TLP/RTO (`rto_min 1ms`로 이미 억제됨) | 0.28ms |

이 스크립트들로는 더 줄이기 어려운 두 가지가 남는다.

1. **커널 틱이 4ms 단위다 (`CONFIG_HZ=250`, Thor·Orin 공통).** RACK 재정렬 대기의 상당수가 이 틱
   반올림으로 보인다. `CONFIG_HZ=1000`으로 커널을 다시 빌드하면 이론상 약 1.8ms까지 줄어들 것으로
   추정되지만, **실제로 시도하지는 않았다** - 실물 로봇 하드웨어의 커널 재빌드는 되돌리기 어렵고 부팅
   실패 위험이 있어 사용자 승인 없이 진행할 일이 아니라고 판단했다.
2. ~~**Orin이 유선이 아니라 Wi-Fi다.**~~ **2026-09, 해결됨.** Thor↔Orin을 이더넷 케이블로 직결해서
   중앙값이 1.64ms→0.57ms로 내려갔다 (위 "유선 직결 링크" 참고). 커널 틱(1번) 문제는 그대로 남아 있어
   꼬리(p90 5.6ms)는 거의 그대로다.

**(2026-09-15 추가검증)** 커널 재빌드 없이 1번을 우회할 방법이 더 있는지 다시 뒤져봤다 - GRO 끄기,
NIC IRQ affinity 이동, 클라이언트 프로세스 전체를 `chrt -f`(real-time)로 돌리기까지 시도했지만 전부
효과 없었거나(GRO/IRQ) 오히려 측정을 망가뜨렸다(`chrt` - 프로세스 자신의 스레드끼리 starvation 일으켜
와이어에서는 1건만 재전송됐는데 클라이언트는 20건을 "유실"로 오탐). `jetson_clocks`/`nvpmodel MAXN`은
애초에 이미 양쪽 다 적용되어 있었다. 세 가지 다 실패로 끝나면서 `CONFIG_HZ=250`이 여전히 가장 유력한
후보라는 결론은 그대로 굳어졌다 - 자세한 표는 `CHANGES_THOR.md` 참고.

## 알려진 한계

- `inject_loss.sh`는 **서버 → 클라이언트** 데이터 유실만 흉내낸다. ACK 유실이나 버스트 유실(연속된 여러
  세그먼트가 한꺼번에 사라지는 경우)은 다루지 않는다.
- 여러 인터페이스가 같은 서브넷에 있는 호스트(이 프로젝트의 Thor처럼 유선+Wi-Fi를 동시에 쓰는 경우)에서는
  `ip route show default`의 순서가 매 호출마다 같다는 보장이 없다. 세 스크립트 모두 **대상 IP로 실제
  가는 경로**(`ip route get <peer>`)를 우선 사용하도록 만들어 뒀지만, 뭔가 이상하면
  `ip route get <peer-ip>`로 실제 인터페이스를 직접 확인할 것.
- `analyze_recovery.py`는 캡처된 파일 하나만 본다. 서버 쪽 tcpdump가 시작되기 전에 일어난 재전송이나,
  캡처 도중 tcpdump가 패킷을 못 따라간 경우(`tcpdump`가 종료 시 출력하는 "N packets dropped by kernel"
  확인 권장)는 반영되지 않는다.
- 방법 1(`request-tcp-recovery`)의 `복구 시간`은 순수 네트워크 값이 아니다. vsomeip 자신의 처리 시간과,
  vsomeip 내부의 정체불명의 송신 지연(원인 미파악 - 발행 루프 자체는 아님, 아래 참고)이 섞여 들어간다 -
  `--cycle`을 충분히 짧게 잡으면(기본값 1ms) 이 영향을 최소화할 수 있다. 자세한 내용과 실측은 위
  "결과: 실측값 > 발행 주기가 왜 중요한가" 참고. 정밀한 순수 와이어 레벨 값이 필요하면 방법 2를 쓸 것.
